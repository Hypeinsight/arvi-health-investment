Connecting Arvi to InfoMedix

Arvi and InfoMedix exchange two things, patients coming in and letters going out, using FHIR as the shared language, joined by the patient MRN and protected by a signed-token gate on every crossing.

FHIR R4 (4.0.1) AU Core aligned SMART Backend Services

Prepared for the InfoMedix technical conversation

The Big Picture

Two Arrows and One Shared Key

Strip away the acronyms and the whole integration is two arrows and one shared key. Everything else, the FHIR resources, the tokens, the mappers, is machinery in service of these.

Patients come in

InfoMedix knows who the patient is. Arvi does not. So patient records flow from InfoMedix to Arvi.

Letters go out

Arvi produces the clinical letter. InfoMedix needs it in the chart. So letters flow from Arvi to InfoMedix.

The shared key: the MRN

The hospital Medical Record Number is the one thing both systems agree on. It is what lets a letter find the right patient.

Ownership

A Clean Division of Ownership

Respecting this line prevents most of the serious problems that occur in integrations like this.

InfoMedix owns patient identity

Who the patient is, their MRN, their demographics, when they were admitted. Arvi will never invent a patient, edit demographics, or decide two records are the same person.

Arvi owns clinical documents

The recording, the transcript, the generated letter, the approval state. Arvi decides what a consultation note contains and hands you the finished document.

Keeping patient creation one-directional means no duplicate records ever appear inside the hospital system, which is a patient-safety benefit, not just a data one.

The Language

FHIR Is a Language, Not a Product

It is agreed JSON shapes plus a REST convention. English is not the translator; English is what the translator speaks. In this integration, FHIR is the language and the mapper is the translator.

Agreed shapes

Without a standard, one system says patient_surname, another lastName. FHIR settles it in advance: it is name[0].family, for everyone.

The mapper translates

FHIR at the edges, an internal shape in the middle. Arvi translates on the way in and out.

Anti-corruption layer

A thin translation boundary so neither system concepts leak into the other design.

Identifiers

Two Identifiers, Two Different Jobs

A DocumentReference carries two coded values that look similar but mean completely different things. Keeping them straight is what makes a letter file correctly.

LOINC 11488-4, what kind

Answers what kind of document this is. Lives in the type field. Issued by LOINC, a global body, so every consultation note anywhere is 11488-4.

MRN SVH-88213, whose

Answers which patient this is about. Lives in the subject field. Issued by each hospital, so it is unique to one person at one hospital.

FHIR always pairs a system with a value, so an MRN can never be mistaken for someone else at another hospital.

The Boundary

One Clean Boundary Between Us

InfoMedix always sees standard FHIR. Arvi translates at the edge and keeps its own internal shape, so neither system constrains the other and the contract between us stays stable.

You send and receive FHIR

Standard FHIR resources at the boundary, nothing Arvi-specific. What you already speak.

Arvi translates at the edge

A mapper converts FHIR to an internal shape and back. FHIR never reaches the core database.

The contract stays stable

Because translation is isolated, a change on either side does not ripple across the boundary.

This is the anti-corruption layer pattern. How Arvi builds it internally is in the appendix, and does not affect what InfoMedix sends or receives.

 Document Structure

      
Formatted Text, or a FHIR Composition?

      
Five of our six letter types have sections: History, Examination, Impression, Plan. FHIR can carry these as a Composition, which is more correct but substantially more work.

    

    

      
Our recommendation: formatted text
A DocumentReference with the sections as headed text. It stays perfectly readable in the chart, with far less machinery.
 Start here

      
Composition, only if you use it
Discrete, separately-addressable sections. Worth the extra work only if InfoMedix actually does something with the structure.

    

    
So we ask directly: do you want discrete sections as a FHIR Composition, or is a formatted text document sufficient?

 Security

      
Security Is a Property of the Connection

      
Not a box the data stops at. Think of a bank: the armoured van, the ID check at the door, what the door lets you into, and the CCTV. Four layers, and this integration has the same four.

    

    

      
1. Transport
TLS 1.2 minimum, 1.3 preferred. Mutual TLS if InfoMedix require it. The armoured van.

      
2. Authentication
OAuth 2.0 client credentials with a signed JWT, not an API key. Proving who you are.

      
3. Authorisation
Least-privilege scopes, for example system/DocumentReference.c and system/Patient.rs. What you may do.

      
4. Accountability
An append-only audit record of every send and receive. Proving what happened.

    

  







  

    

      
 Authentication

      
SMART Backend Services, the Healthcare Standard

      
OAuth 2.0 client credentials with an asymmetric signed assertion, not a shared API key. A wax seal: copying the letter is useless without the signet ring.

    

    

      
A key pair
The private key never leaves its owner. Only the public key is shared. Nobody can forge a signature without the private key.

      
A short-lived token
The caller signs a tiny assertion that expires in five minutes and carries a one-time id, which blocks replay.

      
A JWKS endpoint
Each side publishes its public key at a URL, so signatures can be verified and key rotation is painless.

    

    
This is the same pattern Epic, Oracle Health and most major EHRs use for system-to-system access.

 Security

      
The Security Layer, in One Picture

      
The same gate wraps every crossing, in both directions. What happens once, what happens every few minutes, what happens on every request, and what happens always.

    

    

      
ONCE, AT ONBOARDING
Registration
Each side generates a key pair and shares only the public half. Private keys never leave their owner.

      
EVERY FEW MINUTES
Token exchange
The caller signs a short-lived assertion. The receiver verifies it against the registered public key and issues an access token.

      
EVERY REQUEST
The gate
TLS encrypts the pipe, the bearer token says who is calling, the scope says what they may do.

      
ALWAYS
Audit
An append-only record of every send and receive, so any question about a document can be answered.

    

    
The gate sits on the crossing, not in the chain. The token is a header on the same request that carries the letter.

 Scoping

      
What This Integration Does Not Need

      
A direct integration into a hospital DMR is governed by that hospital infrastructure, not the national stack. Confirming this early avoids a large, unnecessary workstream.

    

    

      
No NASH PKI
National authentication certificates are for national services, not a direct DMR integration.

      
No HPI-O
The organisation identifier is only needed for the Healthcare Identifiers Service and national messaging.

      
No My Health Record
No national conformance testing is required to integrate point to point with InfoMedix.

      
No HL7 v2, unless preferred
R4 FHIR is the baseline. We only fall back to HL7 v2 if InfoMedix specifically prefer it.

    

    
Those are required only for My Health Record, the Healthcare Identifiers Service, electronic prescribing, or national secure messaging.

 The Conversation

      
The Four Questions to Settle First

      
Each of these can change weeks of work. Settling them first turns the rest into detail.

    

    

      
Q1. Push or pull?
Will you push FHIR Patient resources to an endpoint we host, or should we query your FHIR server? This decides whether we build a server or a client.

      
Q2. Your document endpoint?
Do you have a FHIR endpoint we push documents to? What is the base URL, and is there a CapabilityStatement at [base]/metadata?

      
Q3. An appointment feed?
Is there an encounter or appointment feed we can consume? If yes, a clinician opens Arvi and today list is already there with MRNs attached.

      
Q4. Where does the MRN come from?
Arvi needs the MRN to file a letter. We would agree how it reaches us: on the patient push, on an appointment feed, or via a lookup.

 Appendix

      
Inside the Mapper

      
For reference. How Arvi builds the translation layer internally. None of this changes what InfoMedix sends or receives.

    

    

      
Start as a module
A translation folder inside the app. A pure function, easiest to build, test and debug. The right start for one or two partners.

      
Grow to a service if needed
A separate integration service with one adapter per partner, justified once several partners with different transports exist.

      
Never store raw FHIR
Storing received FHIR directly would let a standards committee design our schema. We translate to our own shape first.

    

    
One patients table plus a separate identifiers table. Upsert on the system and value pair, never on name, and repoint identifiers when you send a patient merge. That keeps merges solvable without a painful migration.

  







  

    

      
 Appendix

      
Glossary

      
Plain-English definitions of the key terms in this deck.

    

    
Anti-corruption layerA thin translation boundary that stops one system concepts leaking into the other.
AU CoreThe Australian FHIR Implementation Guide. Profiles base resources for Australian use. Currently advisory.
Base64A way of writing data with safe characters so it can travel inside JSON. FHIR requires it for attachments.
CapabilityStatementA FHIR document describing what a server supports. Usually at [base]/metadata.
DMRDigital Medical Record. A document repository that stores and displays documents, not a full EMR.
DocumentReferenceThe FHIR resource describing a document: type, patient, author, date, and the content or a pointer to it.
FHIRFast Healthcare Interoperability Resources. Agreed JSON shapes plus a REST convention. A language, not a product.
HL7 v2The older pipe-delimited messaging standard, still common in Australian hospitals.
IdempotencyDoing something twice has the same effect as once. Essential when retries can duplicate documents.
JWKSJSON Web Key Set. A URL publishing public keys so others can verify signatures. Makes rotation painless.
JWTJSON Web Token. A small signed message used to prove identity.
LOINCA global coding system for clinical concepts. Used to say what kind of document a letter is.
mTLSMutual TLS. Both sides present certificates, not just the server.
MRNMedical Record Number. The hospital patient identifier and the key that joins the two systems.
OAuth 2.0The standard framework for granting limited access without sharing a password.
OperationOutcomeThe FHIR resource used to return errors and warnings.
Outbox patternWriting a job in the same transaction as the business change, then processing it asynchronously.
private_key_jwtAn OAuth client authentication method using a signed assertion instead of a shared secret.
ScopeA string in an OAuth token limiting what the holder may do, for example system/Patient.rs.
SMART Backend ServicesThe widely adopted standard for securing system-to-system FHIR access.
UpsertInsert if new, update if it already exists. How repeated patient pushes avoid duplicates.
